# ML-модуль: контракт с backend (MVP)

Статус: реализован Python-модуль `ml`; ASR проверен на синтетических записях
([замер](ML_EVALUATION.md)). **Сквозной запуск выполнен; на тестовом TTS-совещании
обнаружены ошибки диаризации и дублирование поручения**.
Аудио и транскрипты обрабатываются локально; внешние API для них не используются.

## Граница модулей

Backend принимает запись, хранит файл и метаданные совещания, запускает ML-задачу,
сохраняет результат, предоставляет редактор протокола и экспорт PDF/DOCX.
ML-модуль принимает локальный путь к записи и дату совещания, возвращает JSON.
Интеграцию Teams/Zoom/Meet оставляем после обработки загруженного файла.

```python
def process_meeting(
    audio_path: str,
    meeting_started_at: str,  # ISO 8601 с часовым поясом, например 2026-09-23T14:00:00+05:00
    speaker_names: dict[str, str] | None = None,
    *, num_speakers: int | None = None,
) -> dict:
    ...
```

`audio_path` указывает на файл, доступный ML-процессу. Для первой интеграции
поддержать WAV/MP3/M4A; конвертацию в mono 16 kHz PCM делает ML через ffmpeg.
`speaker_names` — необязательное соответствие `SPEAKER_00` → имя, которое
редактор может передать при повторной обработке. ML никогда не выводит реальное
имя из тембра голоса без отдельной процедуры идентификации.
`num_speakers` — известное число говорящих (1–32), необязательная подсказка
диаризации. Она не подтверждает корректность разделения конкретных голосов.

## Выходной JSON v1

```json
{
  "schema_version": "1.0",
  "meeting_started_at": "2026-09-23T14:00:00+05:00",
  "status": "completed",
  "speakers": [
    {"id": "SPEAKER_00", "display_name": null},
    {"id": "SPEAKER_01", "display_name": "Айнур Каировна"}
  ],
  "segments": [
    {
      "id": "seg_0001",
      "start_ms": 12400,
      "end_ms": 17900,
      "speaker_id": "SPEAKER_00",
      "text": "Айнур Каировна, проведите совещание с институтом до пятницы.",
      "language": null
    }
  ],
  "tasks": [
    {
      "id": "task_0001",
      "description": "Провести совещание с проектным институтом",
      "assignee_name": "Айнур Каировна",
      "assignee_speaker_id": "SPEAKER_01",
      "assigner_speaker_id": "SPEAKER_00",
      "due_date": "2026-09-25",
      "due_text": "до пятницы",
      "source_segment_ids": ["seg_0001"],
      "needs_review": false
    }
  ],
  "summary": "Обсудили график поставки катализаторов и назначили совещание с институтом.",
  "warnings": []
}
```

- `status`: `completed` или `failed`; при ошибке backend получает код/текст ошибки отдельно, без частичного протокола.
- `speaker_id` в сегменте может быть `null` при перекрытии голосов или неуверенной диаризации.
- `language` — `ru`, `kk`, `mixed` или `null`; заполнять только при проверенном определении языка сегмента. Для MVP допустим `null`.
- `suggested_text` присутствует только когда локальный KazLLM предложил исправление ASR. Исходный `text` всегда сохраняется для проверки; подсказка не заменяет аудио.
- `assignee_name`, `assignee_speaker_id`, `assigner_speaker_id`, `due_date` могут быть `null`. Это требует `needs_review: true`; не подставлять говорящего автоматически как исполнителя.
- `due_date` — дата `YYYY-MM-DD`; относительные сроки вычисляются от `meeting_started_at` в его часовом поясе. Если фраза «на следующем совещании» или «после согласования» не даёт календарной даты, оставить `due_date: null`, сохранить `due_text`.
- `source_segment_ids` обязательны для каждого поручения: по ним пользователь проверит результат по аудио.
- Если одна реплика содержит несколько поручений, возвращать несколько объектов `tasks`.
- `summary` не должен добавлять факты, которых нет в сегментах.

## ML-пайплайн

1. Локально декодировать запись, проверить длительность/формат.
2. ASR: переключаемые Mixed CTC (`asr/rukk`) и multilingual Whisper через `faster-whisper`, таймкоды и VAD. Качество живой шала-казахской речи ещё не измерено.
3. Диаризация: локальный `pyannote/speaker-diarization-community-1`; совместить интервалы говорящих с ASR-сегментами по времени. Сохранять стабильные ID внутри одного совещания.
4. При наличии локального KazLLM получить подсказки по исправлению смешанной речи, сохранив исходный ASR-текст. Это текстовая модель, поэтому она не распознаёт аудио напрямую.
5. Локальная инструкционная LLM извлекает поручения и саммари в JSON по фиксированной схеме. В промпте требовать только факты из транскрипта, исходные сегменты и `null` при отсутствии данных. Валидировать JSON и ссылки на сегменты программно.
6. Нормализовать сроки отдельным кодом/правилом с датой совещания; неоднозначные сроки отправлять на проверку.

Модели скачать и зафиксировать заранее; при демонстрации инференс должен работать
без обращения к внешним сервисам. Нужна проверка лицензий и условий доступа к
конкретным весам до включения их в дистрибутив. Предложенный стек — выбор для
первого прототипа, а не подтверждённое качество на данных кейса.

## Проверка и передача backend

1. ML-разработчик предоставляет запускаемую функцию/CLI `process_meeting`, JSON v1 и инструкцию установки моделей.
2. Вместе с backend-разработчиком проверить один полный цикл: загрузка аудио → обработка → просмотр сегментов/поручений → ручное исправление → экспорт.
3. Отдельно проверить минимум три короткие записи: русский, казахский, смешанная речь; минимум две персоны и одно поручение с явным сроком в каждой. Записать фактические ошибки и время обработки.
4. Предоставленные DOCX использовать как ориентир для ожидаемых поручений и тест извлечения из текста. Это не замена аудиотесту ASR и диаризации. Не коммитить реальные записи и протоколы с персональными данными.

## Что backend может делать сразу

- `POST /meetings` — принять файл и `meeting_started_at`, вернуть `meeting_id`.
- `POST /meetings/{id}/process` — поставить локальную ML-задачу в очередь.
- `GET /meetings/{id}` — вернуть статус и JSON v1.
- `PATCH /meetings/{id}/tasks/{task_id}` — сохранить подтверждённые правки человека.
- `GET /meetings/{id}/export?format=docx|pdf` — экспортировать утверждённый протокол.

Экспорт, напоминания и хранение статусов поручений принадлежат backend; ML лишь
предлагает черновик. Отправлять уведомления только после подтверждения
ответственного и срока человеком.
